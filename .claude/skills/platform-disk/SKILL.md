# platform-disk

Find out what is eating the disk in `datha_platform/`, then reclaim it in tiers — safest first, and only what the user approves.

Written after 2026-09-08, when a Playwright run failed with `ENOSPC: no space left on device` and the machine had **423 MB free of 228 GB**. `.angular/cache` alone held **22 GB** across four frontends. That error looks like a flaky test, which is why this skill exists: check the disk before believing a weird failure.

## Report first (always)

```bash
df -h /System/Volumes/Data | tail -1
du -shc */.angular/cache 2>/dev/null | tail -1      # the usual culprit
du -shc */dist */coverage 2>/dev/null | tail -1
du -shc */node_modules 2>/dev/null | tail -1        # pnpm-deduped; usually not the problem
docker system df                                     # images / containers / volumes / build cache
du -sh ~/Library/Caches/ms-playwright 2>/dev/null
```

Show the table, name the biggest tier, then ask which tier to reclaim. **Never delete before showing numbers** — the point is that the user learns where it went.

## Tiers, safest first

| # | Tier | Command | Cost of deleting |
|---|------|---------|------------------|
| 1 | **Angular build caches** | `rm -rf */.angular/cache` | One cold rebuild per frontend (~30-60 s). Nothing else. |
| 2 | Build output | `rm -rf */dist */coverage` | Regenerated by the next build. |
| 3 | Docker **build cache** | `docker builder prune -f` | Slower next image build. |
| 4 | **Dangling** images (`<none>`) | `docker image prune -f` | Re-pull only if something still referenced them. |
| 5 | Stopped containers | `docker container prune -f` | **Ask first** — may belong to another project; compose recreates them, but container-local state is lost. Volumes survive. |
| 6 | Whole unused image stacks | `docker image rm <name>` | Re-pull cost (bandwidth). **Name them to the user before removing** — e.g. a dormant Supabase stack was 9.4 GB on 2026-09-08. |

**Stop the dev servers before tier 1.** Deleting a cache under a live `ng serve` produces junk rebuild errors that look like real compile failures. Use the `run-platform` stop procedure, prune, then restart only the product being worked on.

## Hard rules

- **Never `docker volume rm`, never `docker system prune --volumes`, never `docker compose down -v`.** Volumes are the user's Postgres / Redis / NATS data. On 2026-09-08 all 11 volumes were active and totalled 417 MB — there is nothing to win there and everything to lose.
- **Never touch another project's containers or images without naming them first.** This machine also runs a Supabase stack and a `pr*` stack that have nothing to do with this platform.
- **Never delete `node_modules`** to free space: pnpm dedupes it to ~3.6 GB total and reinstalling costs far more time than it returns.
- `.angular/cache` is gitignored and regenerable; `dist/` and `coverage/` likewise. Anything tracked by git is off limits.
- Report what was freed (`df` before and after) — a prune with no number is not a result.

## Why caches grow

`.angular/cache` grows per **rebuild**, not per running server, and Angular has no size cap. So it creeps up whoever is running: a long session with many edits fills it faster than five idle dev servers. Running **one product at a time (two at most)** — the standing preference since 2026-09-08 — slows the growth and saves ~1-1.5 GB of RAM per `ng serve`, but does not stop it. Pruning is the actual fix, and it is cheap.
