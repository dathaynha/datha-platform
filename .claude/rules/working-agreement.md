# Working agreement (dathq)

## Git discipline — most important

- Execute ONLY the verb said: "fix" = edit files and stop; "commit" = commit only; "push" = push only; "create branch" = branch only. Never chain the next step.
- "I want to push X later / together" is intent talk, NOT a command. Answering a question is NOT consent to a proposed action. When ambiguous, ask "push now?" and do nothing until answered.
- **Wrong and critical: fix it and push, do not wait for a verb.** (dathq, 2026-09-22.) The
  standing rule is verb literalism, and this is the exception that outranks it: when
  something is both *wrong* — not a preference, a defect — and *critical* — it breaks a
  restore, loses data, leaks a secret, or leaves the platform unrunnable — correct it and
  push without asking. Report what was found and what was done, in that order. The
  judgement to make is not "may I?" but "is this actually both?"; a stale sentence in a doc
  is neither, and a runbook step that leaves two services dead is both.
- Announce the chosen branch name before/at creation.
- One branch per feature (or explicitly grouped work); separate commits per concern.
- If pre-commit hooks run `git add .`, stash unrelated dirty files around each commit.
- **"push" is never standing permission.** One "push" covers exactly that push; every later commit — same branch, same session — waits for a fresh explicit "push". Default after committing is *stop*.
- **"push" always implies `prepare-push` first**, then push only if the review passes.
- **A PR ends the turn.** After creating it: report number/URL and stop. Do not poll pipeline runs, chase Bot Review or tail task logs — dathq watches PRs and reports back. Only dig in when he reports a failure.
- **"back to dev" / "back to main"** = `git checkout main && git pull` in that repo. The pull is pre-authorized by that phrase — the one standing exception to verb literalism.
- **ADO auth failure: ask, never work around.** Tell dathq to `git fetch` and paste his password; never plumb PATs or tokens. The keychain then covers the whole workspace, so one `git fetch` in any repo unblocks all of them. The workarounds he called *"super extreme and BS"* (2026-08-17), each of which burned turns where one sentence would have done: an `az account get-access-token` bearer header, a token-as-basic-auth URL, reading a PAT out of `_local/`, and reconfiguring the credential helper.

## Workflow

- New feature/bug: analyze first, present root cause + plan + concerns, then WAIT for "go".
- The user verifies every change in the running app before anything is committed.
- Temp hacks for testing: mark clearly (`TEMP ... REVERT BEFORE PUSH`), revert on the user's word.
- Local-only tweaks: keep uncommitted, stash before commits.
- Don't run lint/tsc/tests after every edit — only at prepare-push time or when asked (see critical-behaviors #4).
- **Small + clearly correct = do it, don't park it.** A one-line mechanical correctness fix inside the work already in hand gets fixed and reported — not a backlog row, not a footnote. Analyse-then-wait is for *nontrivial* work. If it needs his call, ask **in that turn**; a note at the end of a summary reads as dodging.
- **Where that stops: version bumps, dependency changes, and anything spanning more than one repo.** Present the compatibility evidence *first*, then wait. For Module Federation especially, lead with what actually constrains it (declared `engines`, agent images, whether the risk is even Node-related) rather than with edits. Evidence he accepts: real builds, real suites, resolved lockfile package-sets.
- **"Everything gucci? / no small things left?" is a real audit request**, often asked twice, and it has caught real defects. Do not restate what already passed — run the checks *orthogonal* to the green ones: lockfile **package-set** diff after any dependency change (raw line count misleads), an explicit `tsc` (test runners transpile, they don't typecheck), a **production build** for anything touching build-toolchain deps or typings, and a read of your own diff for dead config copied from a sibling. Then say plainly what you found, including "this one was mine".
- **A regression test must be proven to fail against the old code.** Write it, revert the fix (or stub the old shape), watch it fail with the *expected* message, restore. On 2026-09-06 a bearer-leak spec passed against the buggy code because it only exercised the guarded path — it looked like coverage and was worth nothing. A green new test proves nothing on its own. And it must fail **for the right reason**: on 2026-09-09 a reverted logout fix made three specs fail with `TS2554: Expected 2 arguments, but got 1` — a *compile* error from `toHaveBeenCalledWith(true)` against a two-parameter `logOut`, not the behaviour under test. Red is not evidence until the message is the one you predicted; assert on `spy.calls.mostRecent().args[0]` when a typed matcher fights the signature.
- **A third-party event may not fire the way you assume — and the test is what tells you.** On 2026-09-09 a dialog's stale-input bug was "fixed" with PrimeNG's `(onHide)`, which does **not** fire when the parent lowers `[visible]` — which is how every close in that app works. The regression test failed with the exact original symptom (`Expected: "" Received: "a stale query nobody wants back"`), so the wrong fix never shipped. Prefer a framework-level seam (an `effect` on the input signal) over a library's lifecycle event when the state change originates outside the library.
- **An icon class that does not exist renders nothing, silently.** `pi-microphone-slash` and `pi-phone-slash` are not in PrimeIcons 7, so the muted mic and the end-notice icon were simply blank circles (2026-09-10). Nothing errors, nothing logs. Before using an icon name, check it against the installed set (`grep -oE '\\.pi-[a-z0-9-]+' node_modules/primeicons/primeicons.css`), and prefer a test that asserts the glyph actually paints — `getComputedStyle(el, '::before').content` is `'none'` for a class that does not exist. Note `primeicons.css` must be in the **test** styles for that to work; it was only in the build styles.
- **`backdrop-filter` creates a containing block for `position: fixed`.** The shell toolbar's glass effect silently re-anchored the messenger call dock, so an incoming call rang in the header corner instead of centre-screen (2026-09-10). Anything `fixed` rendered from inside the shell chrome must be re-parented to `body` — and the test for it belongs in the **shell** suite, because a remote running standalone has no toolbar and cannot reproduce it. When a fixed element lands in the wrong place, walk the ancestor chain for `transform` / `filter` / `backdrop-filter` / `contain` rather than adjusting offsets.
- **Chase every intermittent failure to a named cause — including your own tests.** Five specs looked flaky in this session (2026-09-10). Two were **real product bugs** (a send and an inbound frame both lost when they raced the first page fetch), two were **unbounded waits** (`waitForEvent` with no timeout, `expect.poll`'s 5s default against a loaded machine), and one was **a test I had just written** sampling a value once immediately after the action that changes it. None was flakiness. Read the failure artefact first: the page snapshot named the first bug in a single step, after I had already guessed wrong twice.
- **An unbounded `waitForEvent` with a swallowed rejection burns the whole test timeout.** `page.waitForEvent("popup").catch(() => null)` looks harmless: when the popup never arrives the `.catch` hides the failure, so the spec sat for 60s and then failed on an unrelated assertion, which reads as a hang rather than a bug (2026-09-10). Always pass an explicit short `timeout` to a `waitForEvent` whose result is incidental.
- **A repeated pass is evidence; a deterministic test is proof.** The same attachment spec failed 1-in-5, then 4-in-8 while I was guessing at the cause. Reading the failure's page snapshot — the sidebar had the message, the thread did not — named the bug in one step, and a unit spec then pinned it so it can never be dismissed as flake again. When a spec fails intermittently, read the artefact before touching the code, and do not report an intermittent pass as a fix.
- **A Go service does not hot-reload — restart it, or you are testing yesterday's binary.** This has now cost three debugging rounds on the same day (2026-09-11): a screen share that "did not work", and later a relayed field that arrived `undefined` while the source plainly sent it. **Restart the Go service as the first step after editing it**, not as a hypothesis after the evidence gets confusing. On 2026-09-11 screen sharing "did not work" for a real user and then failed in a scripted test too. The code was correct: `realtime-service` had been started 16 minutes *before* the `call.renegotiate` handler was written, so the running binary answered every renegotiation with `unknown_type` and the peer never saw the shared screen. `ng serve` rebuilds itself and trains you to forget that `go run` does not. Before drawing any conclusion about a Go service, compare `ps -o lstart=` for the listener against the mtime of the file you changed.
- **Never start a suite while `ng serve` is still rebuilding.** Two specs "failed" once each and then passed alone and in repeated runs (a read-receipt spec, then an attachment spec, 2026-09-10). Both times the cause was mine: I edited a source file, waited ~10s, and launched Playwright while the dev server was mid-rebuild, so the page loaded a stale bundle. Wait for `✔ Compiled successfully` in `.claude/tmp/run/<repo>.log` *after* the last edit before drawing any conclusion from a run — and never report such a failure as flakiness without checking the build log first.
- **A test that reproduces the wrong state proves nothing.** The skeleton regression test passed against the broken code because the mock loaded the conversation *list* first, and the store resolves a conversation from the list row — so the detail fetch it was meant to be waiting on never mattered. Reproducing a **cold** reload (list, detail and messages all still in flight) made it fail, and doing so exposed a second real fault the first version had hidden.
- **When the user says "best practice", survey the field before designing.** Asked to fix a read tick, the useful move was to check what WhatsApp, Telegram, iMessage, Messenger, Slack and Discord actually do — which showed that read state is a property of the *conversation*, not of every message, and that a standalone status row inside a bubble is something no one ships. The survey also produced the layout answer (bubbles vs single column) with reasons that were about *this* product rather than taste. Do the survey, state the trade-off, then recommend.
- **A test that cannot fail is not a test.** The first version of the composer-spacing check asserted only that the input was visible and then took a screenshot — it would have passed against the very bug it was written for. Rewritten to assert the computed `padding-bottom`, it fails with `Expected: >= 20, Received: 12` against the old layout. If you cannot state the value that changes, you have written a screenshot, not a test.
- **An id that is never equal to anything fails silently, so assert identity end to end.** `oauthService.getIdentityClaims().sub` is the **IdP's** subject; the platform's `owner_id` (`google_<sub>`) only exists in the **gateway-minted access token**. Reading the wrong one 401s nothing — it just never matches, and on 2026-09-10 that surfaced as three separate-looking messenger bugs (same name shown to both people in a direct chat, your own typing indicator echoed back, your own messages rendered as the other person's). When a value's whole job is to be compared, write the test that compares it. → `.claude/docs/services/api-gateway-architecture.md` § The frontend's owner_id
- **State a derived value in one place, and let the owner derive it.** The same bug had a second half: `ChatStore` took its owner id from whichever component remembered to push it in, and the header widget — mounted from login, before any page — never did. A store that resolves its own dependency cannot be left holding an empty string by a caller that forgot.
- **After a formatter runs, an exact-match patch is stale.** On 2026-09-08 three edits silently did nothing because prettier had rewrapped the lines being matched — and one of them (an `activeConversation` fallback) sent me debugging the wrong layer for several rounds. When a scripted edit and a formatter share a file: assert the match, then grep for the new text before drawing any conclusion from a failing test.
- **A linter you did not run is a linter CI will run for you.** prepare-push on 2026-09-15 reported Go "Lint: PASS" on the strength of `go build`, `go vet` and `gofmt -l`, and MegaLinter then failed !183 with `gocritic: exitAfterDefer` — `os.Exit(1)` in a function whose own doc comment says it "owns every deferred cleanup, so a startup failure returns an error rather than calling os.Exit". The code said the rule and I broke it; the linter said so and I had not asked it. Two specifics: `go vet` does **not** include gocritic, and a bare `golangci-lint run` does not either, because with no `.golangci.yml` in the repo MegaLinter's defaults enable more than the local ones — so reproduce with `golangci-lint run --enable gocritic ./...`. And verify a lint fix the way you verify a test fix: revert it, confirm the linter reproduces CI's exact message, restore. Reading `.mega-linter.yml` first is what tells you what actually gates the PR in both directions — it is the same file that proved an unformatted `.scss` was not a blocker.

- **A gitleaks finding lives in a commit, so a follow-up commit cannot clear it.** MegaLinter's gitleaks step scans **git history** (`main..HEAD`), not the working tree. On 2026-09-11 it flagged a golden test vector in `realtime-service` — `base64(HMAC-SHA1("test-secret", …))` in `internal/turn/turn_test.go`, entropy 4.38 — and a new commit carrying the fix still reported `leaks found: 1`, because the unannotated line was inside the original commit's own diff. The fix is to **amend that commit and force-push with `--force-with-lease`**; a `.gitleaksignore` fingerprint is worse, since it pins to a SHA that any rebase invalidates and becomes dead config once the PR squash-merges. Two further points: the directive is `// gitleaks:allow` **on the finding's own line** — on the line above it does nothing, silently; and a golden vector computed *outside* the language under test must keep its literal, because recomputing it in Go would make the assertion circular and delete the interop guarantee the test exists for. Reproduce locally before pushing a lint fix: `docker run --rm -v "$PWD":/repo zricethezav/gitleaks:latest detect --source /repo --log-opts "main..HEAD" --redact`.
- **A computed that recomputes to the same value does not propagate, so an effect that binds DOM can silently never run.** The call dock's `<video>` elements are created when a call turns video — and at that instant nothing the binding effect depended on had *changed* value, so it never re-ran and the viewer's main tile kept a null `srcObject`: one person shared, the other saw black (2026-09-11). Every class and `data-testid` assertion passed the whole time. Two rules came out of it: read the **state object** itself in an effect that must re-run on any transition, not just the derived values you happen to use; and use `afterRenderEffect` when the effect reaches into the DOM, because the element may not exist yet when a plain `effect` fires. Assert the **element property** (`srcObject`, `videoWidth`) — structure assertions cannot see this class of bug at all.
- **Build UI, then LOOK at it — before saying it is done.** On 2026-09-11 dathq found roughly a dozen call-UI defects across eight rounds and said plainly *"way too many bugs babe"*. Every one passed a green unit suite: an unbound `srcObject` showing black, the expanded stage rendering at compact width, an empty video tile on a ring, an avatar vanishing on answer, a camera column so narrow the picture letterboxed into a sliver. Class and `data-testid` assertions cannot see any of that. What worked — and should be the *first* move on any visual change, not the eighth — is to drive it headed with Playwright, **screenshot it, and measure the element**: `getBoundingClientRect()`, `videoWidth`, `srcObject`, `getComputedStyle`. Each round that started with a measurement found its bug in one step; each round that started with reasoning produced another wrong fix for him to report.
- **Same-specificity rules are decided by source order, and a nested rule is not obviously "nested".** Chasing a call-dock width, a rule written earlier in the file lost to one nested inside `.call-dock.is-stage` that compiled to the same specificity (2026-09-11) — the value was simply ignored, silently. Related: `:not()` and `:has()` each contribute their argument's specificity, so `.a:not(.b):has(.c)` outranks `.a.d`. When a CSS value appears not to apply, print the computed value before editing anything; and prefer editing the rule that already wins over adding a competitor.
- **A layout bug is invisible to a passing test suite — screenshot it.** The phase 2.5 call UI passed 135 unit specs while rendering the expanded video call at the *compact* width, because `:not()` and `:has()` each contribute their argument's specificity: `.call-dock:not(.is-ring):has(.call-stage)` is (0,4,0) and silently outranked `.call-dock.is-stage` at (0,2,0). A second defect — a black empty video stage on an incoming ring, before any media flows — was equally invisible. Both were obvious in one screenshot. When the change is visual, drive it headed and **look at it**; assertions about classes and testids prove structure, never appearance.
- **Run one product at a time, two at most** (dathq, 2026-09-08). Each `ng serve` is ~1-1.5 GB of RAM and every rebuild grows that frontend's `.angular/cache`, which has no size cap. "run all" is the exception, not the habit. And when a build or test dies with `ENOSPC`, check the disk before debugging the test: on 2026-09-08 a Playwright run failed that way with 423 MB free and **22 GB** sitting in Angular caches. → `.claude/skills/platform-disk/SKILL.md`
- **A person is shown with their avatar — everywhere, without being asked.** dathq should not have to report this surface by surface, and he has now reported it three times: the chat list and thread header showed a bare letter while the same person's Google picture sat on every bubble (2026-09-10), the call dock showed an initial beside a live call (2026-09-11), and the directory search showed initials while picking who to talk to (2026-09-11). The rule: **any UI that names a person also shows their picture**, resolved from the accounts directory (`ChatStore.pictureUrl(ownerId)` in messenger-frontend, `/api/accounts/users/lookup` behind it) — never from the OAuth claims, which are this user's only. Render it through the shared component (`modules/shared/person-avatar`), which owns the three rules that kept drifting: the directory picture, the initial as fallback, and a failed load falling back rather than leaving a torn-image icon. `lh3.googleusercontent.com` pictures do not always load in a third-party context, so `referrerpolicy="no-referrer"` and an `(error)` handler are not optional — the conversation list had neither. Sizing and shape stay with the caller's wrapper; the component fills it and inherits its radius. Deriving the initial from a display **name** is also part of it: `displayName()` falls back to the raw owner id, so a Google account renders as "G" — pass `initialOverride` where a caller resolves it from the directory itself.

- **A `localhost` default passes on the dev machine for the worst possible reason.** Module Federation's `publicPath` in `messenger-frontend` defaults to `http://localhost:4003/`, and on 2026-09-13 that made the remote unloadable from a phone: `remoteEntry.js` arrived (the shell was told its real URL) and every lazy chunk after it was fetched from `localhost:4003` — which on a phone is the phone, and is blocked as mixed content from an `https://` page regardless. Every same-machine test passed, because there `localhost:4003` *is* the dev server. Before calling any URL-producing default correct, ask **what this resolves to on a different device** — and note that the env var to override it existed already, documented for `build:prod` only, when a remote served from anywhere but localhost needs it in dev too.

- **When the field splits, take a whole camp — mixing two is how you ship an incoherent rule.** Group chat divides cleanly: Messenger/Slack/Teams/iMessage make a group an ad-hoc multi-person conversation, so it needs **two** others and its name can therefore stay **optional** (the derived "Alice, Bob" title always carries two names); WhatsApp/Telegram/Signal make it a first-class object, allow **one** other, and therefore **require** a name. Each pairing is load-bearing. On 2026-09-14 I took the one-other minimum from the second camp and the optional name from the first, and shipped a group that was indistinguishable from the direct chat with that person — dathq reported it with a screenshot within the hour. The survey is not finished when you have a list of what each app does; it is finished when you know **why** each app's rules hold together. Worth noting how the choice actually got made: asked which camp he lived in he said "Messenger, Slack, Teams", and then, after using both in the running app, picked the *other* camp anyway — "I like the force name with the ability to create a group with 2 people better." Familiarity named the default; **trying it** named the decision. Offer the coherent alternatives and let him feel them, rather than settling it from the survey alone.

- **A library's own focus management competes with yours, and the winner changes when the DOM does.** Adding a "New group" row above the compose dialog's search box made *it* the first focusable element, so PrimeNG's `focusOnShow` ran after the manual `onShow()` focus and took it (2026-09-14). Nothing errored; the search box simply stopped being focused on open, and an existing spec caught it with `Expected: focused / Received: inactive`. Two mechanisms were focusing one dialog and neither knew about the other — the fix is to switch the library's off (`[focusOnShow]="false"`) rather than fight it, per configure > compensate. Whenever you insert an element **above** an existing one inside a third-party container, ask what the container does with the first child.

- **A shared RxJS stream keeps its memory after the UI that fed it is gone.** `distinctUntilChanged` is what makes a search box cheap, and it is also what made the *same* query silently return nothing the second time: the dialog cleared its own input and the page dropped the results, but the stream still held the last value, so re-typing it emitted nothing and the list stayed empty with no request and no error (2026-09-14). One box hid this; a second box on the same subject — the group's add-people search — made it the common case. When a stream is shared by more than one surface, **reset it where the surface closes**, not only where it opens, and remember that clearing the *view* state does not clear the *stream* state. Found by a screenshot script, not by any assertion: the spec that now pins it fails `Expected: 3, Received: 0`.

- **Backend built, frontend never wired: the defect no test on either side can see.** `messenger-service` shipped the complete group surface in phase 1 — create, rename, add participants, leave, limits, admin authz — with **40 passing specs**, while `messenger-frontend`'s only create path hard-coded `{ type: "direct" }` (found 2026-09-14). Four endpoints were live, tested and unreachable. Both suites were green because each tested its own half. When a service exposes a capability, the thing to check is not that it works but that **something calls it** — `grep` the frontend for the route before believing a feature exists.

- **A scripted edit bypasses the formatter, and the test suite will not tell you.** Editing TypeScript with `python`/`sed` string replacement produced three files that failed `prettier --check` on 2026-09-14 while all 81 specs passed — vitest does not care about formatting and **MegaLinter fails the PR for it**. Found by the "gucci check", not by anything green. Run `pnpm exec prettier --check` (or `--write`) after any scripted edit to a TS repo, before commit. Two related traps in the same family: a **backtick inside a template literal closes it** — writing `` `joined` `` into an SQL string that lives in backticks produced `TS1005: ',' expected` (2026-09-15); and a scripted patch silently does nothing once a formatter has rewrapped the lines it matches on, so assert the match rather than assuming it.

- **A rename leaves the old exported symbol behind, and the compiler says nothing.** Slice 1 replaced `kv.SetNXWithTTL` with `HJoin`, and the orphan sat in `internal/kv` for a day — together with a test fake implementing it and a comment claiming an interface still required it. **Go does not flag an unused exported method**, `go vet` does not either, and every test passed. The audit found it by grepping the symbol across the repo. After replacing any exported primitive, grep its name: a hit only in its own definition and a test double means it is dead.

- **A bot review that argues with itself mid-paragraph is usually wrong about the headline and right about the smell.** PR-Agent flagged "Missing Parameter" on the `call_participants` upsert (2026-09-15), then walked it back twice in the same comment ("but wait — … they will be inserted, but with `joined = false`", which was the intent). The parameter indexing was correct and no behaviour changed. But a reviewer genuinely could not tell whether unioning the invited and joined arrays was deliberate, and **that part is a fact about the code, not about the reviewer** — so the decision went into a comment plus a spec that fails if anyone "tightens" it. Check every bot finding against the code before accepting *or* dismissing it; the useful yield is often the ambiguity rather than the claimed defect. Never edit working code just to quiet a bot.

- **A test double that *mirrors* logic rather than running it proves nothing about that logic.** The call room's join-with-takeover and conditional-leave are Redis **Lua scripts**, and the unit fakes reimplement their rules in Go (2026-09-14). Every test passed, and would have passed just as happily if the real scripts had a syntax error, called a function the server does not have, or disagreed with the fake about an edge — the suite was asserting that the fake agrees with itself. `internal/kv` sits at 0% coverage precisely because it is the seam where this happens. The fix is not a better fake: it is to run the real thing once, deliberately, and check every branch — `docker exec <redis> redis-cli EVAL "<script>" …` took two minutes and covered takeover, wrong-session, empty-session, superseded-close, holder-close and absent-field. Same rule wherever logic leaves the language: SQL in a string, a Lua script, a shell pipeline, a regex fed to another engine. **If the language under test is not the language that will run it, the unit suite cannot see it.**

- **A transport being connected is not the data having arrived, so poll for the payload.** The four-way mesh looked broken on 2026-09-15: every remote tile reported `videoWidth === 0` and the video track came through `muted: true`, which reads exactly like a failed negotiation. It was not — the assertion sampled once, the instant `call-duration` appeared, and **ICE connecting is what makes the duration appear while the first video frame lands a moment later** (encoder start, then a keyframe). The SDP dump that settled it showed all six links `sendrecv` with audio and video senders on both ends, so nothing was wrong at all. Two lessons: when a measurement of *arriving* data fails, poll it before believing it (`expect.poll`, not one `evaluate`); and dump the protocol state — transceiver directions and m-lines — before theorising about a negotiation, because it is one cheap command and it either names the bug or clears the whole layer.

- **A create that is not idempotent leaks one row per run.** The 1:1 call suite can create freely because a direct conversation is idempotent on the sorted pair. A **group is a first-class object** and `POST /conversations` makes a new one every time, so eight runs of the new group spec left eight identical "E2E Mesh" groups in the dev database (2026-09-15) — the same failure mode as the "E2E Callee" pile-up, reached by a different route, and worse because `messenger-service` has **no conversation-delete endpoint** to clean up with (only `DELETE /conversations/:id/participants/me`, which is *leave*). Where a test cannot delete what it makes, the creation has to be idempotent: list first, reuse what matches, create only when absent. Verified by running it twice and counting the rows — an unverified cleanup fix is exactly the kind that silently does not work.

- **Never `git checkout <file>` to undo a temporary probe.** Reverting a debug instrument that way on 2026-09-15 also discarded the new spec sitting in the same file, which had taken the whole session to write; it survived only because a copy happened to be in `/tmp`. `git checkout` restores the file, not the edit. Remove the probe by deleting the probe — an anchored replace of the block, or an editor edit — and keep `git checkout` for a file you genuinely want back as committed. The same goes for `git stash` on a file holding both.

- **Which repo a component lives in does not tell you where it is rendered.** Module Federation splits those two facts, and a claim that merges them is confidently half wrong. On 2026-09-15 I told dathq "the call dock is mounted by the header widget, which only the shell renders" as the reason to test at :4000 — true of the **dock**, and he corrected it immediately because the **call button** is ordinary thread chrome in `messenger-frontend` and renders fine at :4003. Both halves were about "calling"; only one was about the shell. The check is two greps, not one: find the component's **selector** and see what templates contain it, then find *those* templates' mount points — a component reachable only through an `exposes` entry (`header-widget-entry.ts`) is rendered by the host and by nothing in the remote's own standalone tree, whose root here is a bare `<router-outlet />`. Worth doing before writing any sentence of the form "X lives in the shell" or "X lives in the remote". The same session showed why it is not pedantry: because the buttons render standalone and `WebrtcCallService` is `providedIn: "root"`, :4003 can *start a real call* it has no UI to show or to hang up.

- **A remote must work without the shell — that is what the architecture is for.** Asked how to fix a standalone remote that had a call button and no call UI, I offered "hide the button when not shelled" as a live option; dathq's answer was flat: *"When i create microfrontend like this is for all the small frontend can work independently, with or without the shell. Duh F? Chat can work without the shell, event store can work without the shell."* (2026-09-15). Degrading a remote's own feature because the host is absent is never the fix — the fix is to mount in the standalone tree what the host mounts for it. Anything reached through a `./HeaderWidget`-style expose therefore owes the standalone layout a counterpart mount, and anything ambient the widget does at login (starting the socket, say) owes it that too. Before proposing a "hide it there" option, check whether the capability is the remote's own; if it is, hiding it is a bug being written down as a design.

- **Re-parenting a host element from a constructor is silently undone inside `@if`.** `CallDockComponent` moves itself to `document.body` to escape an ancestor `backdrop-filter` (which creates a containing block for `position: fixed`). Done in the constructor, that worked only because its one caller rendered it **statically**: Angular inserts a host node at its anchor *after* the component is constructed, so the first control-flow mount (2026-09-15) put it straight back where it started, with no error and nothing in the console. `afterNextRender` is the fix and is correct in both cases. Generally: any DOM surgery on your own host element belongs after the first render, never in the constructor, because where Angular will put that element is not decided yet.

- **A dev server that fails to compile keeps serving the last good bundle, so a "passing" test may be testing the code you just broke away from.** Twice on 2026-09-15 a deliberately-broken build reported the test still passing: once because `sleep 6` was not long enough, once because the break left an unused import and the build failed with `TS6133` — in both cases `ng serve` kept the previous bundle and the browser never saw the change. A red-proof run is worthless without confirming the compile: count `Build at` lines in `.claude/tmp/run/<repo>.log` before and after, then check the result says `✔ Compiled successfully` and not `✖ Failed to compile`. Applies to the fix as much as the break.

- **A server-side capability with no caller is not a feature.** Slice 1 built call reconnection properly — `HJoin` treats "same session, new connection" as a reload and hands the place back — and its doc said the client owed it "the `session_id` itself". So slice 3 sent the session id, and I told dathq reload would work. It could not: the live call lived only in an in-memory signal, so a reloaded tab had no idea it had been in a call and never sent `call.join`. The server's takeover path had never once been reached. He found it in a minute by refreshing (2026-09-15). This is the **same shape** as the phase-1 defect where `messenger-service` shipped the whole group surface with no caller in the frontend — and I had that rule written down and still repeated it, because a handover note ("what slice 3 owes it is X") reads like a complete list when it is one person's guess. Before claiming a cross-slice capability works, trace the whole path and find the line that *sends* the frame; a green suite on either side proves only that each half is willing.

- **Reason about what ends the state your test is driving.** A group call ends itself when the second-to-last person leaves (`empty`: a mesh of one is a person looking at themselves), so a test that clicks hang-up on all three participants waits forever for a button the server already took away — surfacing as `locator.click: Test ended` and a bare test timeout with no failed assertion to read (2026-09-15). Two hang-ups and an assertion that the last dock disappears is both shorter and a better test, because it pins the `empty` rule. When a live-stack test times out with no assertion message, suspect an interaction with an element the *server* has removed before suspecting the product.

- **Probe the running state before theorising about the cause.** Chasing that timeout I had three wrong theories (the fake camera contending across contexts, stale Redis call state, a video renegotiation failing) and the history rows showing `0:00` seemed to confirm all of them. One probe — dumping each page's dock text once a second — showed the call perfectly healthy at "3 in the call" and ticking, which eliminated the entire product in one step and left only the test. Those `0:00` rows were from earlier runs that died elsewhere; **artefacts from previous attempts are not evidence about this one.**

- **A fake device never loses the race a real one loses.** Chrome's `--use-fake-device-for-media-stream` opens instantly, is never busy, and is never held by another tab — so `getUserMedia` in a test is effectively free and infallible. That hid an ordering bug for a whole session: the call rejoin awaited capture *before* sending its `call.join`, and on a real machine (no camera, three browsers contending for one microphone) that await either let the frame hit a socket that had moved on — `RealtimeService.send` drops those silently — or failed outright and abandoned the rejoin with nothing on screen. Every automated test passed the entire time dathq was losing his place. The general rule: when a double stands in for a **scarce shared resource** (a microphone, a camera, a port, a lock, a file handle), the property it cannot model is *contention*, so ordering around it has to be reasoned about rather than tested into existence — claim the irreplaceable thing first (here, the place in the room) and let the replaceable thing follow.

- **Say what you verified and in which configuration, not that it works.** I told dathq the reconnect worked three times and was wrong twice, each time extrapolating from the one setup I could drive: a single tab, my own browser, fake media. He has several windows open, a real microphone and no camera. The honest report distinguishes *verified here, in this configuration* from *believed, untested* — and when a fix cannot be reproduced in the failing environment, say that plainly instead of declaring success and asking him to check. Repeated "fixed!" claims that fail on contact cost more trust than the bug did.

- **When a mechanism needs three things to go right and fails silently if any one doesn't, question the mechanism, not the three things.** Auto-rejoin needed an open socket, reacquired capture, and a won takeover; three separate failure modes were found and fixed in one session and it *still* dropped him. dathq's answer was to change the design — Messenger does not auto-rejoin, it shows the ongoing call in the thread and you press Join — which has no race at all and needed no server change, because the live call was already in a read model the thread loads. Before patching the fourth failure mode of a racy mechanism, check whether the product's own conventions already avoid the race.

- **A test that has to win a race to fail is not a regression guard, and the only way to know is to revert and watch.** The live e2e for the ongoing-call banner — three browsers, a bystander, the call ends, the banner must go — **passed against the buggy code** (2026-09-15), because the history projection happened to land before the refetch so the row read as closed anyway. It detects the bug only in the half of runs where the fetch wins that race. The deterministic proof was the unit spec, which fails with `Expected {…} to be null` every time. Keep the live test for what it is worth (it exercises a path no unit test reaches) but say in the test itself that it is not the guard — otherwise the next person reads a green suite as cover it never provided. Same family as "a green new test proves nothing": here the red was *absent*, and only reverting revealed it.

- **A page already open does not pick up a rebuild of a federated remote.** dathq reported the banner still showing for an ended call, from a browser I had launched before the fix (2026-09-15). The data was right — 0 unclosed rows, no Redis keys — and a fresh load of the same page was clean. The tell was in his screenshot: the header's Call buttons were visible *next to* the banner, which the fixed code hides whenever a call is ongoing, so both could only be true of pre-fix code. When someone reports a UI bug from a long-lived tab, establish which bundle it is running before debugging the code — and prefer a screenshot detail that is logically impossible under the new code to arguing about timestamps.

- **A projection that can only be closed by an event it might never receive is permanently wrong the first time that event is lost.** `calls.ended_at` was written by exactly one thing — projecting `call.ended` — published by realtime-service, the process most likely to be the thing that died (2026-09-15). A killed instance published nothing, the Redis record expired in silence, and the row claimed a call was in progress *forever*, so the thread offered Join for a call that had been over for days. dathq saw the pattern before the cause: *"I see this issue occur a lot actually, the data is wrong when there's a bug happen."* Two things came out of it. **Give any such projection a time bound** — a rule applied at read time (cannot fail to run) *and* by a sweep (so the stored data is right too), sharing one function so they cannot drift. And **make the closing reachable by somebody other than the process that opened it**: instance heartbeats plus a reaper, with ending made an atomic claim so concurrent closers announce once. Before shipping a state machine, ask what closes it when the closer dies — and note that "it has a TTL" is not an answer, because **expiry publishes nothing**.

- **When behaviour turns on an ordering comparison, the test data has to sit on the side that exercises it.** The spec pinning "never yield a call you are already in" passed against the buggy code (2026-09-15) because the rival invite came from an owner id sorting *below* self — which the old code refused as `busy` anyway, never reaching the branch under test. Pointing the invite at the id that sorts *above* self made it fail with `Expected '9999…' to be '1111…'`: the old code had abandoned the live call and taken the rival. A green new test proves nothing, and a red one proves nothing until it is red for the predicted reason — but the trap specific to comparisons is that *half* the inputs skip the branch entirely while looking like a complete test. Name which side of the comparison the fixture is on, in the test, in a sentence.

- **A spec that needs a wide viewport must be given one by the command CI runs, not by the one you run.** Five call-dock layout specs passed locally and failed on the agent at the same commit (2026-09-16, PR !188). The dock's presenting layout only exists above `min-width: 60rem`, so those specs need a wide window — and `karma.conf.js` gained a `ChromeHeadlessWide` launcher plus a `package.json` script pointing at it. **CI never used either**: `platform-pipelines`' Angular template hardcodes `--browsers=ChromeHeadless`, an 800×600 window, so the specs hit their own guard and failed with `needs a viewport of at least 960px; got 741px`. The real defect was that **local and CI ran different browsers**; the failures were only the symptom. Two specifics worth keeping: the template exposes `testCommand` as a **parameter**, so the override belongs in the consuming repo's `bot-review.yml` — no `platform-pipelines` change and no tag bump; and shadowing the built-in launcher's own name in `customLaunchers` looks tidier and **recurses** (`RangeError: Maximum call stack size exceeded`), because its base resolves to itself. Before trusting any green suite, run the exact command the pipeline runs.

- **An element can be present, correct, and invisible — so assert geometry, not existence.** Three separate "the stage is blank" reports on 2026-09-16 were the *same* fault: a tile with no definite size inside a flex container, which `overflow: hidden` then clipped to nothing. Measured at `0x0` (both axes `auto`, so the box fell back to the video's intrinsic size — 300×150 with no frames, which is also why the unit tests passed) and at `0x619` (a bare `.call-tile` in a flex row with no width of its own). Each time the spec asserted the element **existed** and passed while the screen was empty. Two rules came out of it: **one axis must be definite** — `width: auto` *and* `height: auto` with an `aspect-ratio` still has nothing to size from — and **every measuring spec asserts a rect, not a selector**. The same session also found a grid laid out on a count that no longer matched its children (`2, 2, 1, 1` rows for six tiles) where a *width* assertion passed and only a **row** assertion failed, because the offending rule keeps the width identical by design.

- **A revert that does not compile is not a red — neutralise the value, do not delete the code.** This recurred three times on 2026-09-16 while red-proofing: removing a fix left an unused constant or a narrowed type and the suite died with a build error instead of a failed assertion, which proves nothing about behaviour. The technique that works is to keep every symbol referenced and change what it *computes* — `Math.min(1, QUIET_SAMPLES)` instead of deleting the hysteresis, returning the old fallback instead of removing the branch. Related and worth noticing: when a tri-state type made the naive revert impossible to compile, that was the **type system enforcing the case** — a good sign about the design, and still not a red.

- **Adding a second kind of activity to a product built around one kind breaks every place the first kind was assumed — and each one looks like its own little bug.** On 2026-09-16 dathq reported four in a row, all the same fault wearing different clothes: a call did not move a conversation up the list (only the message transaction wrote the sort key), the row's timestamp disagreed with its own preview (bound to `lastMessageAt`), the header widget showed a blank preview for a call (its own private `lastMessage?.body`), and signing in mid-ring showed nothing at all (the ring is a fire-and-forget frame, and a ringing call has no history row because that is written when somebody *answers*). Calls had been shipped for weeks; every suite was green throughout. **The move is not to fix them one at a time as they are reported.** When a second activity type lands, grep every derivation of "latest", "ordering", "preview", "unread" and "what happened here" and check each one against the new type — they are all now incomplete, and the user will otherwise find them for you in ones and twos over days. Related: the same session found a **third** copy of the preview rule in the shell's header widget, which is the single-source-of-truth rule below arriving late.

- **Every fire-and-forget fan-out needs a state read on connect, or it is invisible to anyone who was not already there.** `call.incoming` is published over core NATS: it reaches whoever holds a subscription at that instant and nobody else. Someone not signed in is not a slow subscriber, they are *no* subscriber, so calling a person who has not logged in yet rang nothing and left no trace — the caller waited the full 30 s while the callee's screen stayed empty (dathq, 2026-09-16). The fix is never to replay the event: **re-derive from the state**, which is what click-to-join already did for an ongoing call and what `PendingFor` now does on connect. Replaying is actively worse here — the stored offer is stale and the ICE candidates that followed it went to the same dropped subject, so answering it would connect nothing and present as "Connecting…" forever. Ask of any live-state fan-out: *what does somebody who connects one second later see?*

- **A dedupe guard must cover the network write only, never the local reconciliation.** The read watermark is POSTed once per newest-message id, which stops every keystroke re-sending it. That guard sat *above* the line clearing the conversation's unread flag, so once anything restored the dot — a list refetch answering from a watermark write that had not landed yet — nothing could ever take it off again, and dathq was looking at a thread he had plainly read (2026-09-16). Local state is cheap to recompute; only the round trip is worth skipping. Same shape as any cache: dedupe the fetch, never the assignment.

- **A red-proof proves which property is load-bearing, and it will tell you when you are wrong about that.** Docking a chat window needed a box that does not grow with its content, and the spec written for it passed against `height: auto` (2026-09-17) — because `max-height` was doing the bounding all along and the `height` I had reached for was only setting the resting size. Removing *both* failed with `Expected 1711.5 to be less than 757`, which is the real fault and the real message. So when a neutralised fix leaves the test green, the honest reading is not "the test is weak" but **"my claim about which line matters is wrong"** — find the line that is actually holding the invariant, and write the comment about that one. Related and cheap: measure before theorising. A window's 11px horizontal scrollbar survived two guesses about bubble `max-width` and was named in one step by printing `scrollWidth` vs `clientWidth` and then every child whose right edge passed the scroller's.

- **When a second surface appears for state that had exactly one, make the derivation take a key — never copy it.** Phase 3 slice 4 put a docked mini chat window over every page, which is a *second simultaneous thread*, and the chats page held about a dozen `active…` computeds reading `store.activeConversationId()` while the store matched with `activeMessages`, `activeCalls`, `activeTypists` and a single `loadingThread` boolean (2026-09-17). Copying those into the dock is the same mistake this workspace has already paid for three times — the shell's header widget growing its own preview rule, four copies of `auth.interceptor.ts`, the call-label rule living only in `thread.component.html`. The move is a factory over an id (`threadView({ store, realtime, conversationId })`) that the old surface adopts *first*, in its own commit, proven by the existing suite staying green. **And whatever shared resource the old surface used to own outright now needs refcounting**: `openConversation` closed the previous thread's socket subscription, which with two surfaces silently unsubscribes a window still on screen — holders in, holders out, close on the last one. Two specs, each red-proofed: `Expected [ 'c1' ] not to contain 'c1'` for the subscription, `Expected true to be false` for the loading flag that used to be global.

- **A back-compat wrapper kept during a refactor becomes an orphan the moment the last caller moves — and the spec that still calls it is what hides this.** Making the chat store's derivations take a conversation id, I kept `activeMessages`, `activeCalls`, `activeTypists`, `ongoingCall` and `loadingMessages` as thin wrappers "so existing callers keep working", then moved every caller to the keyed accessors or to `thread-view.ts` (2026-09-17). All five were dead, and nothing said so: `tsc` is happy, the linter is happy, and `grep` reports plenty of hits **because the unit spec still exercises them**. The audit check is not "does this symbol have references" but **"does it have a reference that is not its own definition and not a test"** — a wrapper whose only remaining callers are assertions is a wrapper the product does not use. Deleting all five and repointing ~25 spec assertions left 265 specs green, which is the proof they were dead. Do this sweep at the end of any refactor that introduces a parameter where there used to be implicit state.

- **Browser storage a feature invents is not covered by logout, so key it by user instead of hooking logout.** The docked chat windows persisted to one `localStorage` key, and `AuthenticationService.clearAuthData()` removes the session keys and knows nothing about anything a feature added later — so the **next person to sign in on that browser** had the previous person's conversations restored into their dock (2026-09-17, found by the post-build audit, not by any test). Adding a logout hook was the obvious fix and the worse one: it couples a feature to the auth service in all four frontends, and it *throws away* the first user's windows when they come back. Keying the entry by owner id (`messengerChatDock:<ownerId>`) fixes both directions and touches nothing outside the feature. The general rule: **anything a feature writes to per-browser storage needs an answer to "what does the next user on this machine see?"**, and scoping the key is almost always a better answer than clearing it. Red-proofed by collapsing the key back to a shared one: `Expected $.length = 2 to equal 0`.

- **Re-serializing a config file rewrites every line of it, and the diff is the thing reviewers actually read.** Adding four stat panels to `platform-overview.json` produced a **936/583** diff, because the file was written with 1-space indent and escaped unicode and `json.dumps(indent=2)` normalised all of it (2026-09-17). The change was unreviewable and would have looked careless. Match the file's existing serialization — read a few lines first and mirror the indent, the unicode escaping and the key order (`object_pairs_hook=OrderedDict`) — and the same change came out at **358/5**. Generally: when a script edits a structured file a human maintains, the diff is part of the output. Check `git diff --numstat` against what you actually changed before committing, and if the ratio is absurd the serializer is wrong, not the edit.

- **Before deleting a dead string, check whether it names a capability that was never wired.** The audit found `MESSENGER.CALL.SHOW_SCREEN` ("Back to the presentation") with no reference anywhere (2026-09-17). Deleting an unused key is normally trivial — but a string is also the *first* thing written when a feature is designed and the last thing removed when it is dropped, so an orphan can mean "dead copy" or it can mean **"the button was specified and never built"**, which is the same shape as the phase-1 group surface with no caller. Here it was genuinely dead (the shipped stage returns to the shared screen by unpinning, and `UNPIN` is the string that button uses), and confirming that took one grep of the component. Do that grep. The cost of being wrong is deleting the only remaining evidence of a missing feature. Worth pairing with the sweep that finds them: flatten both catalogs, assert the key sets are identical (287/287 caught nothing, which is the point), then grep each leaf key against the component sources.

- **`toBeHidden()` is satisfied by an element that does not exist, so a hidden-assertion made before the page renders passes against the bug.** The first shell mobile spec asserted `expect(page.locator(".shell-sidebar")).toBeHidden()` in the same tick as `goto` (2026-09-17). It passed. It also passed with the fix neutralised, while a probe showed the sidebar right there at `display: flex`, 224px wide — because at that instant Angular had not rendered and the locator matched **nothing**, which Playwright reports as hidden. The red-proof is what exposed it: the run failed on a later width assertion (`Expected: 390, Received: 166`) while the hidden-assertion above it stayed green, and a neutralised fix that leaves an assertion green means that assertion is not the guard. Two habits: wait for a **render anchor** (some element the layout always has) before asserting anything about a page, and pair every `toBeHidden()` with `toHaveCount(1)` so absence cannot masquerade as invisibility. Same family as *a test that cannot fail is not a test*, with the twist that this one cannot fail for a reason that never appears in the diff.

- **Adding a second navigation surface breaks every selector that assumed one, in the tests as much as the product.** The compact bottom bar made `page.locator('nav a[href="/"]')` in `chrome.spec.ts` resolve to two elements and fail with a strict-mode violation (2026-09-17) — the sidebar's Home link and the bottom bar's. Nothing about the sidebar changed; the selector had simply been unique by accident. Before adding a second surface, grep the specs for the bare element selectors (`nav`, `header`, `main`, `[role=...]`) that are about to become ambiguous, and scope them to the surface they mean. Same shape as the rule above it about keying a derivation when a second surface appears — the test suite has the identical problem and reports it as a confusing failure in an unrelated file.

- **A third-party inline style has no CSS override, so route its value through a custom property rather than reaching for `!important`.** PrimeNG's `p-table` takes its floor as `[tableStyle]="{ 'min-width': '52rem' }"`, which lands as an inline style on `<table>` — so the event-store lists stayed 832px wide on a 390px phone no matter how many columns were hidden (2026-09-17). Binding it to `var(--es-table-min-width)` and setting that property in the stylesheet keeps the library's own seam as the seam and puts the breakpoint where every other breakpoint lives, with no specificity fight and nothing to un-pick later. This is *configure > compensate > ignore* applied to CSS: the inline style is the configuration point, so change what it reads rather than out-shouting it. Note the measurement order that got there — hiding the columns first and re-measuring is what proved the floor, not the columns, was holding the width.

- **A helper that reads a signal as its own guard makes every `effect` that calls it depend on what it writes — and a collection rebuilt on a no-op keeps that loop spinning.** `ChatStore.ensurePerson` starts with `if (this.directory().has(ownerId)) return;` and ends with `directory.update(current => new Map(current))`. The call dock calls it from an `effect` for each participant, so the effect **tracked** the directory, and the update returned a fresh Map even when the lookup resolved nobody — signal emits, effect re-runs, asks again: **2187 requests in three seconds**, measured against a mocked gateway on 2026-09-17. Nothing errored and no test saw it; it surfaced only because a probe printed the request log while chasing something else. Two fixes, both needed: wrap the call in `untracked()` so a guard read cannot become a dependency, and **return the same reference when nothing changed**, because "new object every time" turns any such loop from bounded into infinite. In production the trigger is ordinary — an owner the directory cannot resolve, i.e. a deleted account or someone who has never signed in. Generally: before calling a helper inside an `effect`, ask what signals it reads *internally*, not just which ones you passed it.

- **A mocked socket sends nothing it was not told to, so state the product takes from a handshake frame is simply absent.** `WebrtcCallService` learns its own owner id from the socket's `ready` frame. The shell's call-ring spec mocked the socket and never sent one, so `selfOwnerId` stayed `""`; `invitedSet` therefore never added this user, the 1:1 peer could not be picked out of a set of one, and the dock rang with no name. The spec had been failing on `main` against a product that was behaving correctly (2026-09-17). When a spec asserts on identity or on anything derived from "who am I", check that the fixture actually delivers the frame that establishes it — and prove where the fault lies by running the failing spec against a clean tree before touching any source.

- **A Module Federation host does not load a remote's global stylesheet — only component styles travel with the JavaScript.** So anything a remote declares in the files listed under `angular.json`'s `styles` (its `base.scss` and everything that imports) simply **does not exist inside the shell**, with no error and nothing in the console. On 2026-09-17 dathq reported a docked chat window that "opens then gets resized bigger": `--messenger-dock-width` is declared on `:root` in `messenger-frontend/src/styles/base.scss`, so hosted it computed to the **empty string**, `width: var(--messenger-dock-width)` was invalid, and the window fell back to `width: auto` — sizing to its own content and widening as the thread loaded. Standalone at :4003 it was always correct, which is why no existing test saw it. The fix is to put the value somewhere that travels: a **Sass** variable (`styles/_dock.scss`) compiled into each consumer, with the custom property still published from it so the corner stays themeable but nothing *depends* on it. Two consequences worth carrying: a custom property a component needs belongs in that component's own styles or in a Sass constant, never only in a global sheet; and the audit for it is `grep -oE '^\s*--[a-z-]+:' src/styles/*.scss` in every remote, then checking who consumes each one. That sweep immediately found two more — `chatbot-frontend`'s `--app-toolbar-height`, and `--es-table-min-width`, which **I had added the same session**. The test belongs in the **shell's** suite for the same reason as the `backdrop-filter` rule: the standalone remote cannot reproduce it. Red-proofed at `Expected [320], Received [299]`.

- **A card that clips itself cannot host a dropdown, and the damage shows up at the *other* end of the card.** The shell's Settings page grew inline theme and language selects inside `.shell-glass-card.datha-glass-sheen`; the sheen sets `overflow: hidden` so its `::before` is clipped to the radius, and PrimeNG renders a select's overlay **inline, in flow**. Two symptoms from one cause (dathq, with a screenshot, 2026-09-17): the panel was cut off at the card's edge, and — the part that looked unrelated — the card's own icon was pushed *out through the top*, because content 361px tall in a 260px box overflowed both ways. Fixed by dropping the sheen on control cards and taking the overlay out of flow (`position: absolute`, with `position: relative` restored on the card, which the sheen used to provide). Two generalisations: before putting any control with a popup inside a decorative container, check that container for `overflow`, `backdrop-filter`, `transform` and `contain` — the same four to check when a `fixed` element lands in the wrong place; and when a component clips, look for damage at the opposite edge, not only where the overflow started. Red-proofed by re-adding the sheen: `Expected: >= 293.59, Received: 278.59`.

- **A centred flex column pushes its overflow out of *both* ends, and the start edge cannot be scrolled to.** `justify-content: center` plus content taller than the box puts the top of that content at a negative offset, and `scrollTop` cannot go negative — so adding `overflow-y: auto` rescues the bottom and nothing else. On 2026-09-18 the messenger chats stage did this at 667x375: 231px of box for 456px of content, with 113px of it (the icon and the heading) simply gone. Centre with **auto margins on the child** instead — they absorb free space when there is some and collapse to zero when there is not, so the content starts at the top and scrolls. Preferred over `safe center` because it behaves identically everywhere. The measurement that catches it is not "does it overflow" but **"does the child's top sit above the container's top"**; a bottom-edge check passes the whole time.

- **A phone held sideways is wide and short, and width-keyed breakpoints cannot see it.** Every breakpoint in the mobile wave keyed on width, so at 667x375 a landscape phone got the full desktop layout with 375px of height to put it in — and hosted in the shell, 64px less than that. Sweep at `667x375` as well as `390x844`, and reach for `max-height` when the fix is about room rather than width. Related and repeated the same day: **a fix verified standalone is not verified hosted** — the shell adds a toolbar, so the same page has materially less height at :4000 than at :4003.

- **A 44px touch target is what a finger must be able to hit, not how big the control is drawn.** Sizing the messenger thread's buttons to a full 2.75rem gave a header of three large squares beside the avatar and the name, and dathq called it out immediately (2026-09-18). Keep the visible box at its desktop size and carry the reach with a transparent, absolutely-positioned `::after`. The spec then has to assert the **hit area** — `getComputedStyle(el, "::after")` — and that the drawn box is *smaller*; a `boundingBox()` assertion is measuring the ink and will fail the moment the two are separated, which is exactly what it did.

- **A backgrounded command's exit code is not the suite's verdict.** A shell Playwright run moved to the background, exited **0**, and printed a truncated summary; re-run in the foreground it reported **7 failures** (2026-09-18). Four PRs would have gone up broken on the strength of that zero. Read the summary line — `N passed`, `N failed`, and whether the counts add up to the specs that exist — and if a run has been backgrounded or truncated, re-run it in the foreground before calling it green.

- **An unchanged public API does not mean an unchanged DOM, and the tests are where the cost lands.** `@datha/platform-ui` v0.6.0 swapped two dropdowns for chip menus with the same selectors, inputs and outputs, so not one consumer *template* changed — and **nine specs broke** across four repos, because they drove `.p-select` and `getByRole("option")`. Before calling a library change drop-in, grep the consumers for the **rendered** shape, not the API; and give them one shared helper for the new interaction rather than letting each spec learn it separately.

- **Wiring a local build into a consumer for a preview leaves a false green behind it.** To show the new controls, `dist/` was copied over `node_modules/@datha/platform-ui` in two frontends whose `package.json` still pinned the old version. Any suite run in that state tests something CI cannot install. Restore with a real `pnpm install` before running anything you intend to believe, and treat "the installed version does not match the pin" as a blocker, not a detail.

- **"Go" on a design is not "go" on a push.** Asked to build the v0.6.0 control change, I committed, pushed and opened a PR in one motion, and was pulled up for it (dathq, 2026-09-18): *"you push and create PR without my permission, and i havent even checked yet."* The standing rules already say push is never standing permission and that he verifies every change in the running app before anything is committed — the failure was treating approval of the *work* as approval of the *delivery*. When a change is visual, the useful next move after building it is to put it in front of him: wire the local build into a running app, screenshot it, and wait.

- **A fix in one frontend almost certainly belongs in all four.** Each remote carries its **own** copy of `AuthenticationService`, `auth.interceptor.ts` and `http-context.tokens.ts` — there is no shared auth library — so a bug in the shell's copy is a bug in three more repos. This bit twice: the quiet-errors header (2026-09-08, 4 repos) and the local-only logout (2026-09-09, found in `chatbot-frontend`, `event-store-frontend` and `messenger-frontend` by the audit *after* the shell was already "fixed" and the work called done). Before closing any auth, interceptor or session change, `grep -rn` the pattern across **all** frontends.
- **Verification means unit tests *and* the real thing** (dathq, 2026-09-08). A slice is not confirmed by unit specs alone: run the unit suite, then exercise the behaviour end to end — a real HTTP/WS client for a backend, `pnpm test` **plus** the Playwright/e2e suite for anything a browser touches. Faked seams hide exactly the bugs that matter: on 2026-09-08 `messenger-service`'s 31 specs passed while a µs-truncated read watermark left the unread badge permanently lit, because the specs faked the pg pool. Whatever lives in SQL, in a socket frame, or in the browser has to be run to be believed.
- **A service is not verified until it has booted from its own `.env`.** dathq asked on 2026-09-08 how phase 1 could pass with no `.env` files, and he was right to. Every live run that day had env passed **inline on the command line**, which exercises the code but proves nothing about the file: `messenger-service` requires `DATABASE_URL` with **no default** (`z.string().min(1)` → `process.exit(1)`), so it could not have booted from a `.env` that did not exist, while `realtime-service` defaults every var and boots happily with none — meaning the two services fail in *opposite* ways and neither failure would have shown up. Inline env also silently validates nothing about `.env.example` being complete. Boot from the file, with no inline vars, and check the log.
- **`pnpm build` in the frontends is the *development* configuration** (`defaultConfiguration: development` in every `angular.json`). "Build clean" from that command says nothing about budgets, optimisation or the prod AOT path — audits must run `pnpm build:prod`.
- **Verify in headed Chrome, not a VSCode webview.** Drive Playwright headed, seed auth yourself, run the checks and report the result — don't hand him a URL and ask what he sees.

- **A wrapped row cannot be aligned, only replaced.** Both "chaotic" reports in the 2026-09-20 mobile wave — the filter bar and the paginator — were one cause: a `flex-wrap` row hands every line its own width, so no adjustment to the parts can make them line up. The filter bar wrapped into lines of **224px, 296px and 218px** with the actions right-floated to a ragged left edge at x=118; the pager's `justify-content: space-between; width: 100%` *read* as one row and never was, because its two children needed 289px of a 261px host. When a layout looks arbitrary, check whether it wraps **before** touching any of its values, and below the width the row needs, stop being a row.

- **One breakpoint serving two rules is wrong at some width, and it surfaces somewhere that looks unrelated.** The paginator hid its numbered links and stacked into a column at the same `26rem`. Those answer different questions: 26rem is where the *links* stop fitting, 19rem is where the steps and the size select stop fitting *beside each other*. Hosted in landscape the pager gets 329px — comfortably one row — and stacked anyway, whereupon the footer centred a one-line summary against an 84px block and "Showing 1-50 of 722" appeared **between** the steps and the select. Reported as "pagination is a little bit off", which points nowhere near the cause. Give each rule the threshold it actually needs, even when the numbers start out equal.

- **A range-based edit takes whatever happens to sit in the range.** Extracting the duplicated toolbar rules by slicing from `.events-toolbar {` to `.events-toolbar__field {` also removed `.ops-toolbar__advanced` and its grid queries, so the advanced filter panel would have stacked in one column at every width. It compiled, and **all 71 specs passed**, because no spec opens that panel. Found by reading the deletion side of the diff rather than trusting the build. After any cut defined by position rather than by name, read what left — and note the corollary: a green suite says nothing about a surface no spec ever opens.

- **Measure the width you were shown *and* the one you were not.** Three separate reports in one evening — the portrait table, the landscape pager, the filter bar — were each fixed against the single viewport in the screenshot, and one of them then broke the other orientation. Portrait and landscape are different layouts here, not the same layout at two sizes; verify both before calling a responsive fix done.

- **Name a container the moment anything else in the tree is one, because an unnamed `@container` binds to the nearest ancestor and will re-point silently.** `messenger-frontend`'s `.chats-root` had carried an unnamed container since !203, and `call-dock` declares a `container-type: size` of its own; `thread.component.scss` queries `.chats-root` **across a component boundary**, so it was one refactor away from resolving against something else with no error and no log. Named `ms-chats` and `ms-page` on 2026-09-21. Naming also documents the behaviour that was wanted: a docked chat window has no `ms-chats` ancestor, so the thread's rules correctly never match there, and that is now legible rather than accidental.

- **When two mechanisms disagree about what a user gesture means, the gap between their thresholds is a band the user cannot escape.** The chat thread's follow-bottom pin was re-asserted by an `IntersectionObserver` as soon as a bottom sentinel left the viewport by 48px, while `onThreadScroll` only released it past a 120px gap — so every drag that landed between the two was dragged back to the bottom before it could release (`wheel -60: gap 100 -> 0`, measured 2026-09-21; reported as "keeps glitching drag down, takes a while to be able to drag up"). The sentinel leaving the viewport **is** the user scrolling up: the observer could not tell that apart from content growing underneath, which is the case it existed for. The `ResizeObserver` already covered growth, so the fix was to delete the second mechanism rather than to reconcile the thresholds — *when two mechanisms report one event, decide which survives on merit*, applied to a race rather than to noise. The tell that it is this shape: a gesture that works only when it is large or fast.

- **`text-transform: uppercase` on an identifier changes what the identifier says.** The messenger landing page's connector labels are a mix of prose and literals, and the uppercase treatment that suits `write + commit` rendered `createOffer` as `CREATEOFFER` — which dathq spotted — while silently turning `rt.owner.<id>` into a NATS subject that does not exist and `POST /api/messenger` into a path that does not either (2026-09-21). Those two had been wrong for as long as the page existed, because uppercase hides the error inside a style. Best practice is not ambiguous here: identifiers render verbatim, and uppercase is for short prose labels (Material 3 dropped all-caps from buttons outright; Polaris and Carbon keep it for overlines). When a label set mixes prose and code, give the code a modifier rather than rewording it — and note the test has to read `innerText`, because `textContent` returns the untransformed DOM string and would pass against the bug.

- **Setting a width next to insets makes one inset silently inert.** The call dock's desktop stage is defined by four insets (`inset: 1.25rem`) with `width: auto`; the phone rule overrode the *size* to `100%` and left the inset, so `left: 20px` plus `width: 375px` put its right edge at **395px on a 375px viewport** and its bottom 20px below the fold (measured 2026-09-21, reported as the video-call popup being "a little bit off"). When both insets and a width are set, the width wins and the opposite inset is ignored. A rule that sets `border-radius: 0` is announcing a full-bleed takeover; if it does not also reset the inset, it is not one.

- **A route parameter costs a component its state unless the route config is the same object.** Angular's default `RouteReuseStrategy` reuses a component only when `future.routeConfig === curr.routeConfig`, so sibling `chat` and `chat/:id` routes **destroy and recreate the page on every selection**. `messenger-frontend` can afford the ChatGPT-style path segment because its state lives in `ChatStore`; `chatbot-frontend`'s chat page owns the SSE stream, the chunk batcher, the conversation list and the attachment set itself, so the same URL would have torn all of that down. It got the `c` **query param** instead (2026-09-21) — same component instance, so back and forward move between threads under a live page, and `queryParamMap` can be *subscribed* rather than read from the snapshot, which is the opposite of what messenger needs. Before reaching for the nicer URL, ask what the component owns; and route every write of the id through one place, including the send that *creates* a conversation, or a first message is lost on reload.

- **A probe element receives no encapsulated styles, so an instrument can fail the same way the product does.** Measuring the call dock's geometry with a bare `document.createElement("div")` carrying the real class names returned 34px for every state — no `.call-dock` rule applied, because Angular's emulated encapsulation matches on a `_ngcontent-*` attribute the element did not have. Reading that attribute off the live host and stamping it on the probe made the shipped rules apply. The `_ngcontent` trap has now cost four product bugs in one wave and one bad measurement; when a probe reports that nothing is styled, suspect the probe before the stylesheet.

- **`toBeVisible()` is satisfied by whatever is on screen now, including the thing you are waiting to replace.** A spec that clicked the second flow tab and then asserted the links were visible passed instantly against the **outgoing** flow's links, so both passes read the same tab and the label under test was never examined — the assertion that caught it was a separate one checking every expected label had been seen. Anchor a wait on the content that must *change* (`expect.poll` for the new first label), not on the container still being there. Same family as `toBeHidden()` passing against an unrendered element.

- **Compare i18n catalogs as key sets, not by reading them.** `chatbot-frontend` rendered the raw key `CHAT.MODEL_SEARCH_EMPTY` to every English reader whose model search matched nothing, because the string existed only in `de.json` (found 2026-09-21 by flattening both catalogs and diffing: 270 vs 271). ngx-translate renders the key when it is missing — nothing throws, nothing logs, and the surface is one most people never reach. This is the second raw-key bug in two waves after `PROFILE.SUPPORT`, from a completely different cause, which is the argument for making the set comparison a habit rather than a reaction.

## Code style

- Reuse existing patterns/components before writing anything new — grep how the codebase already solves it first.
- Minimum-impact fixes: smallest scoped change that fixes the bug.
- Single source of truth — never duplicate a value/behavior in two mechanisms.
- **Fixing third-party noise: configure > compensate > ignore.** Prefer a setting on the tool; fall back to cleaning up after it only when no setting exists; ignore only when the noise is genuinely rare. And when two mechanisms report one event, decide which one *survives* on merit — do not keep both. This applies to rules too: architecture narratives live in `.claude/docs/`, link, don't copy.
- Never commit mock/fixture data or debug leftovers.
- Comments: one short line max, only for non-obvious constraints.

## Communication

- Concise. Lead with the answer/root cause. No fluff.
- Explain WHY alongside fixes (root cause, trade-offs, blast radius when asked).
- Flag side effects and leftovers honestly and let the user decide.

## Platform intent

This is a personal platform for trying new tech with best-practice structure — strictness is the point. Prefer the "correct" pattern over the expedient one; there is no large-team constraint forcing compromises.

Proactively suggest best-practice improvements when spotted (the user will most likely agree) — but always confirm before applying. Suggest, then wait for "go".

- **A verification command that finds nothing may be querying the wrong thing, so prove the check against a known-good state before trusting its silence.** `run-platform`'s preflight said `curl -s localhost:8222/jsz?streams=1` should list `EVENTS` and `DLQ`; that endpoint returns **totals with no stream names at all** unless `acc=$G` is passed, so the check found nothing on a perfectly healthy NATS and would have been read as "the topology is gone" — prompting a `pnpm reconcile` that was never needed (found 2026-09-18 while writing the new-machine guide). Absence of a match is not evidence of absence of the resource. The habit: run every verification command once on a machine where the thing is known to be present, and make sure it actually succeeds; a check that has only ever been run against a working system and *failed* is not a check. Two mechanical traps in this one line: `$G` must be single-quoted or the shell eats it, and NATS pretty-prints its JSON, so `"name":"EVENTS"` never matches — the key has a space after the colon.

- **A viewport breakpoint stops telling the truth the moment anything sits beside the element, and in this workspace something always does.** Three products broke identically at 667x375 on 2026-09-18/19, and it took finding the third to name the cause: the shell puts a 224px sidebar beside every remote, so a landscape phone reports 667px while the content has 443px. `event-store`'s tables kept six desktop columns in 334px and its table container measured **0px tall at top=549** behind `overflow: hidden`; `chatbot`'s chat column was crushed to **117px** by a fixed `sm:w-72` history pane, wrapping its own subtitle one word per line; `messenger`'s stage measured **119px** — within two pixels of chatbot's, from the same cause. Every one of them looked correct standalone, which is why no suite caught any of them. **Reach for `@container` whenever the rule is about how much room an element has**, and keep `@media` for what it genuinely describes — `max-height` for a short viewport, `pointer: coarse` for touch. Declare the container on the element that owns the layout (`.es-table-wrap`, `.chats-root`, chatbot's `:host` — each the flex parent), not on `:host` by reflex. Container context **crosses component boundaries even though styles do not**, so `thread.component.scss` can query `.chats-root` declared in another component — and where no ancestor container exists, as in the docked chat window, the rule simply never matches, which is usually the behaviour wanted. The guard belongs in the **shell's** suite, same as the `backdrop-filter` rule, because the standalone remote cannot reproduce any of it.

- **`container-type: inline-size` makes an element's width independent of its contents — so a shrink-to-fit box collapses to zero, and a zero-width container then matches its own narrow query.** The new ops paginator declared the container on `:host` and, as a plain flex child of the pager footer, measured **0px wide**; the `@container (max-width: 26rem)` rule meant to hide the page links on a phone therefore hid them at *every* width, which looks exactly like a selector that does not match. The fix is to make the width come from the layout — `flex: 1 1 auto` with a `min-width` — not from the content the containment is deliberately ignoring. Same family as the table that measured 0px tall: **a container needs a definite size on the axis it contains.** Note also that `container-type` implies layout containment, so it makes the element a containing block for absolutely positioned descendants — check for `position: absolute` children before adding it, the way you would before adding `transform` or `backdrop-filter`.

- **A dev server caches a failed module resolve, so a component created in stages can serve with no styles at all while the log says "Compiled successfully".** Writing `ops-paginator.component.ts` before its `.html` and `.scss` existed left webpack with `Can't resolve …component.scss?ngResource`; the later builds succeeded and the page still rendered the component **unstyled**, with page links stacked vertically. The tell is in the DOM, not the log: **`_ngcontent-*` was missing from every element**, which is what Angular does when a component has no styles — so encapsulated rules match nothing and `:host` rules do nothing either. A restart fixed it. When a brand-new component's styles appear not to apply, check for the encapsulation attribute before debugging the CSS, and restart the server rather than trusting a green build that followed a red one.

- **A blanket rule at higher specificity silently defeats every modifier class beneath it — route the value through a custom property instead of fighting it.** `.es-table .p-datatable-tbody > tr > td` declares `color` at (0,3,2); `.es-table__secondary` on the cell is (0,2,0) and can never win, so the ops lists rendered every cell `rgb(30, 41, 59)` and had no visual hierarchy at all — hosted *and* standalone, for as long as those classes existed. The diagnostic that named it in one step: **`font-size` from my rule applied while `color` from the same declaration block did not**, which can only be another rule, never a selector problem. The fix is the `--es-table-min-width` seam again — declare `--es-cell-ink` on an ancestor so it inherits, have the winning rule read it, and let a class on the cell set it, where nothing competes. Prefer that to `!important` or to out-specifying a rule you also own.

- **Know which checks actually gate a PR before deciding what a warning means.** The Angular template's steps are setup → unit tests → **knip** → **e2e** → MegaLinter → PR-Agent, with `knip` and `e2e` defaulting to `true` and no consumer overriding them — so both gate, and a dead export or a failing spec fails the run. There is **no production build step**, which means `anyComponentStyle` budget warnings (event-store hit 11.69 kB against a 10 kB warning budget on 2026-09-19) are local-only and cannot yellow anything; the error budget is 48 kB. MegaLinter enables `TYPESCRIPT_PRETTIER`, `JSON_PRETTIER` and `YAML_YAMLLINT` only — **`.scss` and `.html` are not linted**, so formatting them is optional and formatting `.ts`/`.json` is not. Read `.mega-linter.yml` and the template rather than inferring from what failed last time.

- **PrimeNG's paginator cannot show boundary pages, and the only knob is `pageLinkSize`.** Its page links are a fixed sliding window with no ellipsis, so a 15-page list offers "1 2 3 4 5" and no hint that 15 exists — dathq rejected it on sight (2026-09-19). There is no template hook for the links, so the component has to be replaced rather than configured; `event-store-frontend/src/modules/shared/ops-paginator/` is the one written for it, and it is the pattern to copy if another list needs paging. Two behaviours worth keeping: changing page size preserves the **record** you were looking at rather than the page number (page 3 of 50 is record 101, which at 10 a page is page 11), and the numbers are replaced by a "3 / 15" readout — not clipped — when the container cannot hold them.

- **A build step that only ever runs on a clean tree hides its own bug, and the thing it breaks is silent.** `event-store`'s `build` was `tsc && mkdir -p dist/db && cp -r src/db/migrations dist/db/migrations` — which is correct exactly once. `cp -r src dst` copies *into* `dst` when `dst` already exists, so from the second build onwards every new migration landed in `dist/db/migrations/migrations/` and `pnpm migrate` skipped it without a word (found 2026-09-19, when migration `005` would not apply). CI builds from scratch and would never have shown it; a developer or a production box that builds twice gets a database one migration behind and a service that boots against a schema it does not have. Two generalisations: **`cp -r` into a possibly-existing directory needs `rm -rf` first or a trailing `/.`**, and any script whose correctness depends on the target *not* existing should be run twice before it is believed. The same session produced two smaller instances of "run it, do not reason about it": `SELECT fn($1)` fails with `function fn(unknown) does not exist` because **a bound parameter has no type until you cast it** (`$1::int`), and a backtick inside a template literal closed an SQL string again.

- **A statistic computed from a different number than the one you acted on is a lie the tests will happily agree with.** Switching retention from `DELETE FROM events WHERE timestamp < cutoff` to dropping whole monthly partitions, I reported `eventsDeleted = eventsCandidates` — the rows *past the cutoff* — when what actually went was the rows *in the dropped partitions*. On a clone: 64 candidates, 59 removed, because a partition that still holds live rows keeps its old ones until the whole month expires. Every unit test passed, because the mock returned whatever the code asked for. It was found by counting the table before and after against real Postgres. **Report what you did, not what you intended**, and when a change makes two previously-identical numbers diverge, say in the type and the doc that they are *meant* to differ. Related and worth stating once: partitioned retention changes the granularity of a TTL from the day to the partition — a "90 day" policy keeps some rows for up to 120. That is a product decision wearing an infrastructure costume, so write it down where someone reading the TTL config will see it.

- **"Numbered pages or cursor?" is usually a false choice — a long list is two lists.** Told the `COUNT(*)` fix would cost the numbered paginator, I built the cap and stopped there, and dathq then remembered why he had shipped Previous/Next originally: *"the best practice for a big ass list should be like that. But for normal list the new pagination is the best."* Both true, and the first cut had a real gap between them — at the cap **Next disabled**, stranding a reader at page 200 with rows still below, which is worse than the control it replaced. The shape that holds: **numbers cover what was counted, a keyset cursor takes over past it.** Page numbers need a total, a total needs a count, and the count is what the cap refuses to finish — so the numbers end exactly where the certainty does, and nothing pretends otherwise. Specifics worth keeping: the cursor is **opaque** or clients start building them and the sort order becomes a breaking change; a malformed cursor is a **400**, never a quiet reset to page 1, because a deep page that restarts at the top reads as data loss; keyset needs a **total order**, so the sort gains a tiebreak column and the index has to match; use the **row-comparison** form `(a, b) < ($1, $2)` rather than the expanded `OR`, because the index seeks on it directly and it cannot be got subtly wrong at the boundary; and **Previous is a stack pop**, the only exact "back" available when there is no total to subtract from. Generally: when a constraint forces a worse control, check whether it forces it *everywhere* or only past some threshold — and hand over at the threshold rather than degrading the whole surface.

- **When a performance fix and a shipped UI disagree, the UI is the constraint — say so before building.** Asked to fix `COUNT(*)` on every page, the textbook answer is keyset paging, and it is wrong here: keyset cannot produce page numbers or a total, which is exactly the paginator dathq had asked for two days earlier after rejecting PrimeNG's for having neither. The move that keeps both is to bound the count instead — `SELECT count(*) FROM (SELECT 1 … LIMIT cap + 1)`, reading at most `cap + 1` rows whatever the table holds, with a flag saying it hit the ceiling so the UI renders "10,000+" rather than a confident wrong number. Counting one row *past* the cap is what distinguishes "exactly 10,000" from "at least 10,000"; an off-by-one here silently mislabels an exact total as capped. Deep `OFFSET` is bounded by the same cap, because the links stop there. Generally: before adopting the standard fix for a scaling problem, check what it costs the surface that already exists, and price the alternative that keeps it.

- **`@use` cannot be nested, so a partial that is included inside a rule has to become a mixin.** Migrating this workspace off the deprecated Sass `@import` (Dart Sass 3.0 removes it) was trivial for four files and not for two: the ops list pages pull `primeng-table-overrides` and `table-empty-overlay` in **inside** `:host ::ng-deep`, because a Module Federation host never loads a remote's global stylesheet and those rules have to compile into the component. `@use` must precede every rule in a file, so there is no direct translation. The answer is to wrap the partial in `@mixin`, `@use` it at the top for the namespace, and `@include` it exactly where the old `@import` sat — which matters beyond tidiness, because **`@use` hoists a module's CSS to the top of the output while `@include` emits at the call site**, and these particular rules are meant to win a same-specificity tie on source order against a mixin included above them. Verify a styles migration by **compiling both versions with the `sass` CLI and diffing the emitted CSS**: byte-identical output turns "I think this is a no-op" into a fact, and it is far cheaper than chasing a computed value through the browser. (I did chase one — a `display` that resolved to `flex` where the partial said `block` — and the diff proved it pre-existing and unrelated in one command. Note the tell from the earlier rule held: `position` and `inset` from the *same* declaration block applied while `display` did not, which can only be another rule.)

- **A budget that flags the architecture instead of the bloat teaches you to ignore budgets.** `anyComponentStyle` sat at a 10 kB warning while the two ops list pages compiled to ~11.3 and ~11.7 kB — and about **6.5 kB of each was shared partials that must be inlined per component**, because a Module Federation host never loads a remote's global stylesheet. The number predated the constraint. Raising it to 16 kB with the error budget untouched at 48 kB is configuring the tool correctly, not silencing it; what would be wrong is leaving a permanent warning nobody can act on sitting in every build. Check *why* a budget is exceeded before either raising it or splitting files: if the answer is "a rule the architecture forces", the budget is the thing that is wrong.

- **An enabled control that does nothing is worse than a disabled one, because it says the opposite of the truth.** Two of these shipped in the same paginator and were caught on review of !207. The hand-over to cursor paging was gated on `totalCapped`, which is a fact about the *service*, when the real precondition is `hasNextCursor` — a fact about whether this caller can actually follow one. The DLQ list is capped and has no cursor paging, so it bound neither the input nor the output: its Next stayed enabled on the last page and emitted into an output nobody had subscribed to. **An Angular `output()` with no subscriber fails completely silently**, so nothing logged and nothing threw; the only symptom was a button that did not work. The second was subtler: Next and Last shared `isLast()`, which on a capped list is deliberately false on the last numbered page because the cursor takes over — but Last has nowhere left to jump to, so it sat enabled on the page it would have taken you to, clicking through to a `goToPage` that early-returns. Two rules out of it: **gate a capability on evidence the capability exists**, not on a condition that usually coincides with it; and **two controls that happen to agree today should not share a predicate** — they answer different questions, and the day they diverge one of them lies. Worth noting the reporter's mechanism was slightly wrong (they expected a redundant re-fetch, the early return meant there was none) and the defect was entirely real: check a finding against the code before accepting *or* dismissing it, because the claim and the bug can differ while both point at the same line.

- **A `timestamptz` partition bound is parsed in the session's TimeZone, so the same DDL builds different partitions for different callers.** `CREATE TABLE ... PARTITION OF events FOR VALUES FROM ('2027-05-01')` looks absolute and is not: under `America/New_York` that partition really ran to `2027-06-01 04:00+00`, and under `Asia/Ho_Chi_Minh` a partition named for March held the last seven hours of February (measured 2026-09-20). The damage was downstream and invisible — retention derives a partition's upper bound from its **name**, so at a negative offset the real bound is *later* than the name implies and the daily drop removes rows that have not expired, reporting success. Build such bounds as **explicit `+00` text**, take the month window from `now() AT TIME ZONE 'UTC'` rather than local `now()`, and where a name is used as a key, **add a check that the name and the real bound agree** so the assumption stops being an assumption. The general rule: any value a database re-parses from a literal — a partition bound, a default, a check constraint, a generated column — is evaluated in whatever settings the session happens to carry, so pin the ones that change meaning.

- **A wrong bot finding can still be standing on a real bug — check the claim, then check its neighbourhood.** PR-Agent reported that `generate_series(date, date, interval)` would fail as ambiguous and abort migration `005` and app boot. It was wrong on the facts (`timestamptz` has `typispreferred = t`, so resolution is defined, not lucky) and wrong on the consequence (the migration had already run three times against real Postgres 16, and a fresh database booted to `/health` 200 during the check). Dismissing it there would have been reasonable and would have missed that **the surrounding date handling was genuinely timezone-dependent** in a way that loses data. Disprove the claim with a command rather than an argument — `SELECT typispreferred`, a fresh-database migration run, a boot probe — and then ask what the reviewer might have been smelling. Same shape as the 2026-09-15 finding that argued with itself: the headline was wrong and the neighbourhood was worth the trip.

- **A field you can see but cannot select on is half a feature — and the fix is usually generic, not another parameter.** `origin` was added to the file events so an audit could tell a chatbot attachment from a messenger one, and it landed unfilterable: the events list filters columns and `origin` lives in `payload`. The tempting fix is an `?origin=` param, which is wrong twice — most events have no origin, so it would be a filter that is empty for nine rows in ten, and it repeats the whole conversation for the next payload field somebody adds. A **GIN index on the JSONB document** (`jsonb_path_ops`) plus containment matching makes every key filterable at once. Two traps in that: **containment is type-strict while a query string is always text**, so `payload.duration_seconds=0` compared as `"0"` silently never matches the number `0` — match both the string and the JSON scalar it parses to, and use a strict numeric test so `" 1 "` stays a string; and **a filter you cannot honour must 400, not be ignored**, because a silently dropped filter returns *more* rows than asked for, which reads as the filter being broken rather than as a bad request. Worth noting the key never needs to reach the SQL text at all when you match by containment — it is part of a bound JSON value, so there is no identifier to quote.

- **`aria-label` replaces the visible text as the accessible name, so a row of chips can all announce identically.** Every filter chip on the ops lists carried `aria-label="Remove filter"`, which reads well in isolation and means that with four filters active a screen reader user hears the same button four times with no way to tell which removes which. It surfaced because a Playwright test tried to address one chip by role and name and could not — **if `getByRole` cannot distinguish two controls, neither can a screen reader**, which makes that failure a finding rather than a test problem. Name the thing being acted on ("Remove filter: payload.origin: messenger"), and treat an accessible name that is constant across a repeated control as a defect.

- **An encapsulated style cannot reach a control the component library built, because that element has no `_ngcontent` attribute.** The 2026-09-18 fix that raised `.datha-input` from 25.3px to 38px was written as an ordinary component rule, and on 2026-09-20 it turned out to have covered only the inputs written in the template: the one inside `p-autocomplete` was still 25.3px next to a 38px neighbour, and `.p-select-label` kept the 11px dense tokens inside a host that *had* taken the 38px min-height — so the placeholder sat at the top of a box half again its height, which is what "not centered" meant. The tell is the same one as the blanket-cell-rule bug: **the host resizes and its inner label does not**, from what looks like one rule. Put sizing for any third-party control under `:host ::ng-deep`, which matches both the elements Angular stamped and the ones the library created — and when a library control looks wrong, check for `_ngcontent` on the specific element before debugging the CSS.

- **Probe a hit target at the extremes of *both* axes — one axis fixed is not fixed.** PrimeNG renders a select's clear icon as a bare 16px `<svg>`, and everything the icon does not cover belongs to the select, so a near-miss opens the menu rather than clearing — which a person experiences as "the X needs two clicks". I padded it to 28x28, wrote a spec that clicked 3px from the **left edge**, watched it go red against the old 16px target, and reported it fixed. dathq came back with the same complaint, because a 28px icon centred in a 38px control still leaves a **5px band above and below**, and clicking a few pixels high is exactly what a hand does. The spec had only ever moved horizontally. Two rules: a hit-target spec must click near **each** edge, top and bottom included, and assert the target's height against the control's, not just its width; and **padding applies to an inline `<svg>`** (a replaced element, like `img`), so the target can fill the control while the glyph keeps its size — but size it to the control's *content* box, because padding to the full height overflows and grows the host, which then stops matching the inputs beside it. Worth noting how the second report was reproduced: not by re-reading the CSS but by clicking at a measured offset from the icon's centre and printing whether the label cleared and whether the overlay opened. The first probe that only moved horizontally reported everything working, twice.

- **A `@container` query with no container fails silently, so the rule you wrote simply never runs.** The payload filter's narrow-stacking rule looked correct and did nothing, because the only element declaring `container-type` on that page is `.es-table-wrap` and the filters are not inside it. Nothing errors, nothing logs, and the layout is merely wrong at narrow widths. After writing any `@container` rule, **walk the ancestor chain for a `container-type` and assert the rule actually takes effect at the width it names** — a screenshot at one width is not enough, because the failure looks identical to "this width is fine".

- **A signal's empty state is `""`, and a component library's "is there a value" test is usually `!= null` — so an empty string renders as a value.** The payload field's clear button appeared on a fresh page load, beside the placeholder, with nothing to clear; pressing it did nothing, which is indistinguishable from a broken button (dathq, 2026-09-20, with a screenshot). PrimeNG's `showClear` asks `modelValue != null`, and `""` passes that. Bind `signal() || null` wherever a signal backs a library control whose empty state matters, and assert the affordance's **count**, not its appearance — what was wrong was that it existed at all. Generally: when a library decides whether to render something from your model, find out what it actually tests, because "empty" in a signal and "empty" in that component are rarely the same value.
